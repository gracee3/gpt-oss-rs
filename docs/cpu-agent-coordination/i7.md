### Blocking correctness failures

1. Cross-runtime greedy token parity is prompt-sensitive and fails.
   - Default llama.cpp evaluation of the 444-token, three-turnover prompt
     produces
     `[200005, 35644, 200008, 976, 1825, 19471, 33749, 220]`; the first
     divergence is output token 6 (`19471` versus native `5181`).
   - Forcing llama.cpp physical microbatch size one makes that 444-token case
     match native, but does not close the broader gap. With physical
     microbatch one, 122-, 262-, and 346-token probes still diverge, while a
     136-token probe matches.
   - Native scalar, AVX2, and AVX-512 produce the same 444-token-prompt
     sequence, so that case is not SIMD dispatch variation. The remaining
     evidence is a shared, prompt-sensitive prefill/model-semantic parity gap;
     it is not a monotonic 128-token window boundary failure.
2. Standard Chat Completions tool history fails before inference.
   - A request containing a function declaration plus assistant/tool history
     returns HTTP 500 immediately:
     `harmony error: Tools should have a name!`.
   - `ChatMessage` loses the tool author/name required by Harmony rendering.
3. Responses tool execution does not terminate/parse correctly.
   - A forced `get_weather` function request samples the `<|call|>` token
     (`200012`) but continues generating instead of finishing the call.
   - After 64 tokens it returns HTTP 500 in 60.93 s:
     `Unexpected token 12606 while expecting start token 200006`.
   - Because the first stored function call cannot complete, the required
     follow-up containing real tool history cannot be exercised.
