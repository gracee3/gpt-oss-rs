## Residual-Q8 expert-parity closure

The CPU runner now has internal `q8`, `residual-q8`, and `exact-bf16` expert
projection modes. The existing `CpuModelRunner::load` signature is preserved;
an options loader is available to the parity runner. Residual Q8 is the
internal production default and has no server-facing mode flag. Exact BF16
streams directly from the existing 17-byte repack records into the established
FP32 reduction lanes and remains diagnostic-only. The repack format, layout,
and source cache code are unchanged; the warm cache remains 10,152,370,204
bytes.

The first exact diagnostic run exposed missing BF16 boundaries inside SwiGLU.
After rounding the scaled gate, sigmoid, gated product, linear add, and final
product like PyTorch, exact BF16 restored the complete `harmony_262` sequence:
`[200005, 35644, 200008, 976, 1825, 8967, 33749, 220]`. The step-6 exact run
took 12:11.78, peaked at 11,761,712 KiB RSS, and reported zero swaps. Its
step-6 context ends in token `8967` and its logits select `33749` over `261`.
The corrected official trace refresh took 12:25.28, peaked at 12,408,960 KiB
RSS, reported zero swaps, and confirms the same step number and 268-token
selecting context.

The exact step-6 trace records each selected expert's gate/up, SwiGLU, down,
and weighted output. The remaining end-to-end `1e-5` trace miss occurs before
the experts: layer-0 attention context differs in one BF16 value by
`0.00048828125`. A bounded cache diagnostic localized that to 9 K and 11 V
values out of 65,536 each, originating in the existing RMS/dense reduction
order. The temporary cache surfaces were removed. This residual diagnostic
difference does not change any of the official greedy tokens and is not an
MXFP4 decode or expert-projection mismatch. It leaves the exact expert-stage
tolerance diagnostic open, but the project owner accepted that seam for the
experimental mainline baseline on 2026-08-11 because the CPU kernel
architecture is being reconsidered. Trusted mode remains blocked.

### Implemented corrections

- Chat messages now preserve nullable assistant content, `name`,
  `tool_call_id`, and multiple assistant `tool_calls`. Validation maps each
  result ID to its function name before Harmony rendering and returns HTTP 400
  for missing, duplicate, mismatched, or unresolved metadata.
- `/v1/chat/completions`, `/v1/chat/completions/tools`, and `/tools` now use the
  same Chat implementation.
- The engine uses a terminal-token set. Harmony `<|return|>` (`200002`) and
  `<|call|>` (`200012`) terminate generation; `<|end|>` (`200007`) does not.
  A call finishes as `tool_calls`, including when sampled at the token limit.
- Length-limited Harmony output is parsed without synthesizing a terminal
  marker. Chat returns `finish_reason=length`; Responses returns
  `status=incomplete` with `reason=max_output_tokens`, including the streaming
  `response.incomplete` event. Hidden partial analysis is not exposed as Chat
  content.
- The checked-in parity manifest pins exact Harmony text and token-ID hashes
  for 63-, 122-, 136-, 262-, 346-, and 444-token prompts plus a 180-token tool
  history prompt. The native runner, memory-bounded official PyTorch oracle,
  llama.cpp comparison, and opt-in layer trace keep generated data outside
  Git.
- The first 122-token trace mismatch was layer 0 YaRN rotary arithmetic. The
  native implementation now matches the official reference's float32
  frequency construction and BF16 cosine, sine, multiply, and add/subtract
  boundaries. A position-121 BF16-bit operator regression and exact
  full-prompt token regression lock the correction.
- Automatic dispatch now resolves the i7 hybrid plan: AVX-512/VNNI for BF16
  matvec, Q8 quantization, and RMS norm, with AVX2 for MXFP4/Q8 expert dots.
  Forced paths remain uniform. The public immutable plan is logged at startup,
  while the existing compatibility `path()` still reports AVX-512/VNNI.
